## 1. 서론

### 1.1 문서 목적

본 문서는 KRIBB 바이오정책 인텔리전스 및 생명공학생태계 모니터링 시스템(BEMS) 구축 프로젝트의 요구사항을 정의합니다. 이 문서는:

- 프로젝트의 범위와 목표를 명확히 정의
- 시스템이 충족해야 할 기능적·비기능적 요구사항 명시
- 개발팀, 사용자, 이해관계자 간 공통 이해의 기준 제공
- 시스템 설계, 개발, 테스트의 기준 제시

### 1.2 문서 범위

**포함 사항**:
- 9개 핵심 모듈의 기능 요구사항
- 시스템 전반의 비기능 요구사항 (성능, 보안, 가용성 등)
- 데이터 및 인터페이스 요구사항
- 법규 및 표준 준수 요구사항

**제외 사항**:
- 상세 시스템 설계 (별도 설계서에서 다룸)
- 구현 세부사항 (개발팀 재량)
- 하드웨어 사양 (인프라 설계서 참조)

### 1.3 독자 대상

- **프로젝트 관리자(PM)**: 범위 관리, 일정 수립
- **시스템 아키텍트**: 시스템 설계 기준
- **개발팀**: 구현 기준
- **QA팀**: 테스트 케이스 작성
- **사용자(정책연구자)**: 시스템 이해 및 검증
- **이해관계자(경영진, 부처)**: 의사결정 참고

### 1.4 참조 문서

- ISP 보고서 (2025.12.17)
- 사용자 워크숍 회의록 (2025.11.15 ~ 12.05)
- OECD.AI 시스템 분석 보고서
- EU JRC Bioeconomy Monitoring 방법론
- 정보시스템 구축·운영 지침 (행정안전부)

### 1.5 용어 정의

| 용어 | 정의 |
|------|------|
| BEMS | Bio-Ecosystem Monitoring System, 생명공학생태계 모니터링 시스템 |
| DSS | Decision Support System, 의사결정지원시스템 |
| NLP | Natural Language Processing, 자연어처리 |
| TRL | Technology Readiness Level, 기술성숙도 (1-9단계) |

## 2. 이해관계자 요구사항

### 2.1 이해관계자 식별

| 이해관계자 | 역할 | 주요 관심사항 |
|-----------|------|--------------|
| **KRIBB 정책연구자** | 주 사용자 | 업무 효율화, 사용 편의성, 정확한 분석 결과 |
| **KRIBB 센터장** | 의사결정자 | 정책 품질 향상, ROI, 국제 위상 제고 |
| **KRIBB 원장** | 승인자 | 전략적 가치, 예산 정당성, 대외 평판 |
| **국가바이오위원회** | 최종 사용자 | 근거 기반 정책 자료, 시의성, 신뢰성 |
| **12개 부처 담당자** | 협력 기관 | 데이터 연계, 정책 조정 지원, 정보 공유 |
| **과기정통부** | 예산 당국 | 사업 정당성, 성과 지표, 타 기관 확산 가능성 |
| **IT 운영팀** | 시스템 관리자 | 운영 안정성, 유지보수 용이성, 보안 |
| **외부 전문가** | 자문 위원 | 방법론 타당성, 국제 수준 품질 |

### 2.2 이해관계자별 요구사항

#### 2.2.1 정책연구자 (Primary User)

**SR-USER-001**: 글로벌 정책 정보 검색  
> 정책연구자는 특정 국가, 기간, 키워드를 입력하여 관련 정책 문서를 **3초 이내**에 검색할 수 있어야 한다.

**SR-USER-002**: 일일 정책 브리핑 수신  
> 시스템은 매일 오전 9시에 전일 수집된 주요 정책 정보를 **이메일 또는 포털**로 제공해야 한다.

**SR-USER-003**: 이슈 등록 및 추적  
> 정책연구자는 신규 이슈를 5분 이내에 등록하고, 진행 상황을 **실시간**으로 확인할 수 있어야 한다.

**SR-USER-004**: 정책 시뮬레이션 실행  
> 정책연구자는 예산 배분 시나리오를 입력하고, **10분 이내**에 시뮬레이션 결과를 확인할 수 있어야 한다.

**SR-USER-005**: 보고서 자동 생성  
> 시스템은 분석 결과를 기반으로 **워드/PDF** 형식의 보고서를 **자동 생성**할 수 있어야 한다.

#### 2.2.2 경영진 (센터장, 원장)

**SR-EXEC-001**: 실시간 대시보드  
> 경영진은 생태계 건강도, 주요 이슈 현황을 **한눈에** 파악할 수 있는 대시보드를 제공받아야 한다.

**SR-EXEC-002**: 모바일 접근  
> 대시보드는 **태블릿 및 모바일**에서도 접근 가능해야 한다.

**SR-EXEC-003**: 정책 권고안 요약  
> DSS는 복잡한 분석 과정 없이 **1-2페이지 요약본**으로 핵심 권고안을 제공해야 한다.

#### 2.2.3 국가바이오위원회

**SR-COMM-001**: 회의 자료 지원  
> 시스템은 회의 안건별로 **근거 데이터 및 시뮬레이션 결과**를 2일 이내에 제공할 수 있어야 한다.

**SR-COMM-002**: 국제 비교 자료  
> 주요 정책 이슈에 대해 한국과 주요국(미국, EU, 중국, 일본)의 **비교 분석 자료**를 제공해야 한다.

#### 2.2.4 부처 담당자

**SR-MINISTRY-001**: 데이터 연계  
> 시스템은 부처별 정책 정보를 **API 또는 파일 업로드**로 연계할 수 있어야 한다.

**SR-MINISTRY-002**: 권한별 접근  
> 부처 담당자는 자신의 부처 관련 정보만 열람할 수 있도록 **권한 관리**가 되어야 한다.

#### 2.2.5 IT 운영팀

**SR-OPS-001**: 시스템 모니터링  
> 운영팀은 시스템 상태(CPU, 메모리, 응답시간)를 **실시간**으로 모니터링할 수 있어야 한다.

**SR-OPS-002**: 자동 백업  
> 시스템은 매일 자동으로 데이터를 백업하고, **30일간 보관**해야 한다.

**SR-OPS-003**: 장애 알림  
> 시스템 장애 발생 시 운영팀에게 **즉시** 이메일/SMS로 알림해야 한다.

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 요구사항 분류 체계

**우선순위 정의**:
- **Critical (P0)**: 시스템 핵심 기능, 필수 구현
- **High (P1)**: 주요 기능, Phase 1-2에서 구현
- **Medium (P2)**: 중요하나 후순위, Phase 3에서 구현
- **Low (P3)**: 선택 사항, 운영 중 추가 검토

**MoSCoW 방법론**:
- **Must have**: 반드시 구현
- **Should have**: 가능한 구현
- **Could have**: 여유 있으면 구현
- **Won't have**: 현 범위 제외

---

### 3.2 Module 1: 국내외 정책정보 실시간 모니터링

#### 3.2.1 정보원 관리

**FR-M1-001**: 정보원 등록 및 관리 (P0, Must have)  
> 시스템 관리자는 새로운 정보원(URL, 분류, 수집 주기)을 등록하고 수정·삭제할 수 있어야 한다.

**FR-M1-002**: 정보원 카테고리 분류 (P0, Must have)  
> 정보원은 다음 카테고리로 분류되어야 한다:
> - 국제기구 (OECD, WHO, WIPO 등)
> - 주요국 정부 (미국, EU, 일본, 중국, 한국 등)
> - 싱크탱크 (RAND, McKinsey 등)
> - 학술기관
> - 기타

**FR-M1-003**: 정보원 활성화/비활성화 (P1, Should have)  
> 시스템 관리자는 특정 정보원의 수집을 일시 중지하거나 재개할 수 있어야 한다.

#### 3.2.2 웹 크롤링 및 데이터 수집

**FR-M1-004**: 자동 웹 크롤링 (P0, Must have)  
> 시스템은 등록된 정보원을 설정된 주기(일 1회 기본, 최대 일 3회)로 자동 크롤링해야 한다.

**FR-M1-005**: 변경 감지 (P0, Must have)  
> 시스템은 페이지 변경을 감지하여 신규 또는 업데이트된 문서만 수집해야 한다.
> - 방법: HTML 해시 비교, 게시일 추출

**FR-M1-006**: 다양한 포맷 지원 (P0, Must have)  
> 시스템은 다음 파일 형식을 수집하고 처리할 수 있어야 한다:
> - HTML, PDF, DOCX, PPTX
> - XML, JSON (API 응답)

**FR-M1-007**: RSS/Atom 피드 구독 (P1, Should have)  
> 시스템은 정보원이 제공하는 RSS/Atom 피드를 우선적으로 활용해야 한다.

**FR-M1-008**: API 연동 (P1, Should have)  
> 시스템은 정보원이 제공하는 RESTful API를 통해 데이터를 수집할 수 있어야 한다.
> - 예: OECD.Stat, World Bank API

**FR-M1-009**: 크롤링 오류 처리 (P0, Must have)  
> 크롤링 실패 시 시스템은:
> - 3회까지 재시도
> - 실패 로그 기록
> - 관리자에게 알림 발송

#### 3.2.3 문서 처리 및 분류

**FR-M1-010**: 텍스트 추출 (P0, Must have)  
> 시스템은 PDF, DOCX 등 문서에서 텍스트를 추출해야 한다.
> - PDF: OCR 불필요한 텍스트 기반 PDF 처리
> - 복잡한 레이아웃: 표, 그림 캡션 포함

**FR-M1-011**: 다국어 처리 (P0, Must have)  
> 시스템은 최소 다음 언어를 지원해야 한다:
> - 영어, 한국어, 중국어, 일본어

**FR-M1-012**: 자동 문서 분류 (P0, Must have)  
> 시스템은 수집된 문서를 ML 모델로 자동 분류해야 한다:
> - **정책 유형**: 전략, 법령, 예산, 규제, R&D 프로그램, 기타
> - **기술 분야**: 레드바이오, 그린바이오, 화이트바이오, 그레이바이오, 범용
> - **대상 국가/기관**: 자동 추출
> - **분류 정확도**: F1 Score ≥ 85%

**FR-M1-013**: 수동 분류 수정 (P1, Should have)  
> 정책연구자는 자동 분류 결과를 검토하고 수정할 수 있어야 한다.
> - 수정 이력은 모델 재학습에 활용

**FR-M1-014**: 엔티티 추출 (P0, Must have)  
> 시스템은 문서에서 다음 엔티티를 자동 추출해야 한다:
> - 조직명 (예: NIH, FDA)
> - 기술명 (예: mRNA, CRISPR)
> - 금액 (예: 5억 달러)
> - 날짜 (예: 2025년 1월)
> - 인명 (선택 사항)

#### 3.2.4 메타데이터 관리

**FR-M1-015**: 메타데이터 자동 생성 (P0, Must have)  
> 수집된 각 문서에 대해 다음 메타데이터가 자동 생성되어야 한다:
> - 문서 ID (UUID)
> - 제목
> - 출처 URL
> - 수집 일시
> - 게시 일시
> - 문서 유형 (정책/보고서/뉴스 등)
> - 분류 태그
> - 언어
> - 파일 크기
> - 해시값 (중복 방지)

**FR-M1-016**: 메타데이터 검색 (P0, Must have)  
> 사용자는 메타데이터 필드로 문서를 검색할 수 있어야 한다.
> - 예: "2024년 미국 FDA 규제 문서"

#### 3.2.5 알림 서비스

**FR-M1-017**: 실시간 알림 (P1, Should have)  
> 중요 정책 문서 수집 시 지정된 사용자에게 즉시 알림을 발송해야 한다.
> - 채널: 이메일, Slack
> - 트리거: 특정 키워드 포함, 예산 변동 ±10% 이상

**FR-M1-018**: 일일 다이제스트 (P0, Must have)  
> 시스템은 매일 오전 9시에 전일 수집된 정책 정보 요약을 이메일로 발송해야 한다.
> - 수신자: 전체 정책연구자
> - 내용: 제목, 출처, 1줄 요약, 링크

**FR-M1-019**: 주간 이슈 브리핑 (P1, Should have)  
> 시스템은 매주 월요일 주요 이슈를 정리한 브리핑을 발송해야 한다.

**FR-M1-020**: 알림 구독 관리 (P1, Should have)  
> 사용자는 알림 유형, 키워드, 국가별로 구독 설정을 커스터마이징할 수 있어야 한다.

#### 3.2.6 저장 및 검색

**FR-M1-021**: 원본 파일 저장 (P0, Must have)  
> 수집된 원본 파일(PDF, HTML)은 S3에 영구 보관되어야 한다.

**FR-M1-022**: 전문 검색 (P0, Must have)  
> 사용자는 문서 본문에서 키워드로 전문 검색(Full-text search)을 할 수 있어야 한다.
> - 검색 엔진: Elasticsearch 또는 OpenSearch
> - 응답 시간: 95th percentile < 2초

**FR-M1-023**: 고급 검색 (P1, Should have)  
> 사용자는 다음 조건을 조합하여 검색할 수 있어야 한다:
> - 날짜 범위
> - 국가/기관
> - 문서 유형
> - 분류 태그
> - Boolean 연산 (AND, OR, NOT)

**FR-M1-024**: 검색 결과 정렬 (P1, Should have)  
> 검색 결과는 다음 기준으로 정렬 가능해야 한다:

> - 날짜 (최신순/오래된순)
> - 제목 (가나다순)

**FR-M1-025**: 유사 문서 추천 (P2, Could have)

### 3.3 Module 2: 신규 아젠다 발굴 및 이슈 브리핑

#### 3.3.1 토픽 모델링

> - 토픽 수: 자동 결정 (HDBSCAN)

**FR-M2-002**: 신규 토픽 탐지 (P0, Must have)

**FR-M2-003**: 토픽 라벨링 (P1, Should have)

**FR-M2-004**: 토픽 시계열 분석 (P0, Must have)

> - 검증: PubMed 등 학술 DB와 교차 확인

**FR-M2-007**: 키워드 동시 출현 분석 (P2, Could have)

#### 3.3.3 국가별/시기별 아젠다 추적

**FR-M2-008**: 국가별 토픽 비교 (P0, Must have)

**FR-M2-009**: 선도 국가 식별 (P1, Should have)

> 3. 이해관계자 (누가 영향을 받는가?)

**FR-M2-013**: 브리핑 편집 (P0, Must have)

**FR-M2-014**: 브리핑 발송 (P0, Must have)

### 3.4 Module 3: 정책플랫폼 이슈 관리 및 모니터링

#### 3.4.1 이슈 등록 및 관리

**FR-M3-001**: 이슈 등록 (P0, Must have)  
> 정책연구자는 다음 정보를 입력하여 이슈를 등록할 수 있어야 한다:
> - 제목 (필수, 200자 이내)
> - 카테고리 (필수): 규제, 예산, R&D, 인프라, 인력, 국제협력, 기타
> - 우선순위 (필수): 긴급, 높음, 중간, 낮음
> - 담당자 (필수)
> - 관련 부처 (복수 선택)
> - 설명 (선택, 5000자 이내)
> - 첨부파일 (선택, 최대 10개, 각 50MB)
> - 마일스톤 (선택)

**FR-M3-002**: 이슈 조회 (P0, Must have)  
> 사용자는 이슈 목록을 다음 기준으로 조회할 수 있어야 한다:
> - 전체 이슈
> - 내가 담당한 이슈
> - 내가 생성한 이슈
> - 특정 부처 관련 이슈

**FR-M3-003**: 이슈 검색 (P0, Must have)  
> 사용자는 제목, 설명, 담당자, 관련 부처로 이슈를 검색할 수 있어야 한다.

**FR-M3-004**: 이슈 필터링 (P0, Must have)  
> 사용자는 다음 조건으로 이슈를 필터링할 수 있어야 한다:
> - 카테고리
> - 우선순위
> - 상태 (등록, 진행, 보류, 완료)
> - 기간 (등록일, 마감일)

**FR-M3-005**: 이슈 수정 (P0, Must have)  
> 이슈 생성자 또는 담당자는 이슈 정보를 수정할 수 있어야 한다.
> - 수정 이력 자동 기록

**FR-M3-006**: 이슈 삭제 (P1, Should have)  
> 관리자는 이슈를 삭제할 수 있어야 한다.
> - 소프트 삭제 (실제 DB에서 삭제하지 않고 상태만 변경)

#### 3.4.2 이슈 상태 관리

**FR-M3-007**: 상태 전이 (P0, Must have)  
> 이슈는 다음 상태를 가지며, 지정된 전이 규칙을 따라야 한다:
> - 등록 → 진행
> - 진행 → 보류 또는 완료
> - 보류 → 진행
> - 완료: 최종 상태 (변경 불가)

**FR-M3-008**: 상태 변경 알림 (P0, Must have)  
> 이슈 상태가 변경되면 담당자에게 알림을 발송해야 한다.

**FR-M3-009**: 마일스톤 관리 (P1, Should have)  
> 이슈에 여러 개의 마일스톤을 추가할 수 있어야 한다.
> - 마일스톤 정보: 설명, 기한, 완료 여부

**FR-M3-010**: 마일스톤 진행률 계산 (P1, Should have)  
> 시스템은 완료된 마일스톤 비율을 자동 계산하여 진행률을 표시해야 한다.

#### 3.4.3 이슈 협업 기능

**FR-M3-011**: 댓글 작성 (P0, Must have)  
> 사용자는 이슈에 댓글을 작성할 수 있어야 한다.
> - 댓글 수정/삭제 가능
> - 작성 시간 자동 기록

**FR-M3-012**: 멘션 기능 (P1, Should have)  
> 댓글 작성 시 @사용자명으로 특정 사용자를 멘션할 수 있어야 한다.
> - 멘션된 사용자에게 알림 발송

**FR-M3-013**: 파일 첨부 (P0, Must have)  
> 이슈 및 댓글에 파일을 첨부할 수 있어야 한다.
> - 지원 형식: PDF, DOCX, XLSX, PPTX, JPG, PNG
> - 최대 크기: 50MB/파일

**FR-M3-014**: 활동 로그 (P1, Should have)  
> 이슈의 모든 변경 사항(상태 변경, 댓글, 담당자 변경 등)이 시간순으로 기록되어야 한다.

#### 3.4.4 관련 정보 자동 연계

**FR-M3-015**: Module 1 연계 (P1, Should have)  
> 이슈 등록 시 입력한 키워드를 바탕으로 Module 1에서 관련 최신 정책 문서를 자동 추천해야 한다.
> - 표시: 이슈 상세 페이지 우측 "관련 문서" 섹션

**FR-M3-016**: Module 4 연계 (P2, Could have)  
> 이슈와 관련된 R&D 과제, 법령, 기업이 자동으로 연결되어야 한다.

#### 3.4.5 대시보드 및 리포팅

**FR-M3-017**: 이슈 현황 대시보드 (P0, Must have)

> - 상태별 이슈 수 (파이 차트)

**FR-M3-018**: 간트 차트 (P1, Should have)

**FR-M3-019**: 월간 보고서 생성 (P1, Should have)

> - 내용: 신규/완료/지연 이슈 통계, 주요 이슈 요약

### 3.5 Module 4: 이슈 연관 분석

#### 3.5.1 지식그래프 구축

**FR-M4-001**: 온톨로지 정의 (P0, Must have)  
> 시스템은 다음 엔티티 유형과 관계를 정의한 온톨로지를 구현해야 한다:
> - **엔티티 유형**: 정책, 법제도, R&D 과제, 기술, 경제지표, 기업, 기관, 인물
> - **관계 유형**: 영향(influences), 의존(depends_on), 경쟁(competes_with), 협력(collaborates_with), 규제(regulates), 지원(supports)

**FR-M4-002**: 자동 엔티티 추출 (P0, Must have)  
> 시스템은 정책 문서에서 엔티티를 자동 추출하여 지식그래프에 추가해야 한다.
> - NER 모델 활용

**FR-M4-003**: 관계 추론 (P1, Should have)  
> 시스템은 규칙 기반 또는 ML 모델로 엔티티 간 관계를 자동 추론해야 한다.
> - 예: "A 법안이 B 산업을 규제한다" → (A)-[regulates]→(B)

**FR-M4-004**: 수동 엔티티/관계 추가 (P1, Should have)  
> 정책연구자는 지식그래프에 엔티티와 관계를 수동으로 추가할 수 있어야 한다.

#### 3.5.2 연관 분석

**FR-M4-005**: 이슈 중심 연관정보 조회 (P0, Must have)  
> 사용자는 특정 이슈를 선택하면, 다음 연관 정보를 확인할 수 있어야 한다:
> - 관련 정책 문서
> - 관련 R&D 과제 (NTIS 연계)
> - 관련 법령
> - 관련 기업
> - 관련 기술 트렌드

**FR-M4-006**: 영향 경로 분석 (Path Analysis) (P1, Should have)  
> 사용자는 두 엔티티 간의 영향 경로를 조회할 수 있어야 한다.
> - 예: "바이오파운드리 정책"이 "합성생물학 기업"에 영향을 미치는 경로
> - 알고리즘: 최단 경로, 모든 경로 (최대 depth 3)

**FR-M4-007**: 유사 이슈 발견 (P1, Should have)  
> 시스템은 현재 이슈와 유사한 과거 이슈를 자동 추천해야 한다.
> - 방법: 지식그래프 구조 유사도 + 텍스트 유사도

#### 3.5.3 시각화

**FR-M4-008**: 네트워크 그래프 시각화 (P0, Must have)  
> 연관 정보는 인터랙티브 네트워크 그래프로 시각화되어야 한다.
> - 라이브러리: D3.js, Cytoscape.js
> - 기능: 줌, 팬, 노드 클릭 시 상세 정보 표시

**FR-M4-009**: 레이아웃 옵션 (P2, Could have)  
> 사용자는 그래프 레이아웃을 선택할 수 있어야 한다.
> - 옵션: Force-directed, Hierarchical, Circular

**FR-M4-010**: 그래프 필터링 (P1, Should have)  
> 사용자는 특정 엔티티 유형 또는 관계 유형만 표시하도록 필터링할 수 있어야 한다.

### 3.6 Module 5: 바이오경제 생태계 시스템 다이내믹스 맵

#### 3.6.1 SD 모델 구축

**FR-M5-001**: 인과관계 지도 (CLD) 작성 (P0, Must have)  
> 시스템은 바이오경제 생태계의 주요 변수 간 인과관계를 CLD로 표현해야 한다.
> - 포함 요소: Stock, Flow, Feedback Loop (Reinforcing, Balancing)

**FR-M5-002**: Stock-Flow 모델 구현 (P0, Must have)  
> 시스템은 Vensim 또는 PySD를 이용하여 Stock-Flow 다이어그램을 구현해야 한다.
> - 주요 Stock: 연구인력, 바이오기업 수, 누적 특허, 시장 규모

**FR-M5-003**: 방정식 정의 (P0, Must have)  
> 각 Stock과 Flow에 대한 수학적 방정식이 명확히 정의되어야 한다.

**FR-M5-004**: 파라미터 추정 (P0, Must have)  
> 모델 파라미터는 2015-2024년 역사적 데이터를 기반으로 추정되어야 한다.
> - 방법: 최소자승법, 민감도 분석

**FR-M5-005**: 모델 검증 (P0, Must have)  
> 구축된 모델은 역사적 데이터와의 피팅 오차가 RMSE < 10%를 만족해야 한다.

#### 3.6.2 시뮬레이션 실행

**FR-M5-006**: 기본 시뮬레이션 (P0, Must have)  
> 사용자는 기본 설정(현재 추세 유지)으로 10년간 시뮬레이션을 실행할 수 있어야 한다.
> - 실행 시간: 5초 이내

**FR-M5-007**: 파라미터 조정 (P0, Must have)  
> 사용자는 다음 파라미터를 조정하여 시뮬레이션을 실행할 수 있어야 한다:
> - R&D 예산 증가율
> - 규제 강도 지수
> - 민간 투자 매칭 비율

**FR-M5-008**: 시뮬레이션 기간 설정 (P1, Should have)  
> 사용자는 시뮬레이션 기간을 5년 ~ 20년 범위에서 선택할 수 있어야 한다.

#### 3.6.3 결과 시각화

**FR-M5-009**: 시계열 그래프 (P0, Must have)  
> 주요 Stock 변수(인력, 기업 수, 특허, 시장 규모)의 시간 추이를 선 그래프로 표시해야 한다.

**FR-M5-010**: 다중 시나리오 비교 (P0, Must have)  
> 사용자는 여러 시나리오를 동시에 실행하고, 결과를 겹쳐서 비교할 수 있어야 한다.

**FR-M5-011**: 데이터 내보내기 (P1, Should have)  
> 시뮬레이션 결과를 CSV, Excel 형식으로 내보낼 수 있어야 한다.

#### 3.6.4 민감도 분석

**FR-M5-012**: 일원 민감도 분석 (P1, Should have)  
> 시스템은 각 파라미터를 ±20% 변화시켰을 때 주요 지표의 변화를 계산해야 한다.

**FR-M5-013**: Monte Carlo 시뮬레이션 (P2, Could have)  
> 파라미터에 확률 분포를 부여하고 10,000회 시뮬레이션을 실행하여 결과의 분포를 제시해야 한다.

### 3.7 Module 6: 바이오기술 분야별 기술성숙도(TRL) 대시보드

#### 3.7.1 기술 분류 및 데이터 수집

**FR-M6-001**: 기술 분류체계 정의 (P0, Must have)  
> 시스템은 다음 기술 분류체계를 지원해야 한다:
> - 1차 분류: 레드, 그린, 화이트, 그레이 바이오
> - 2차 분류: 세부 기술 (예: mRNA, 유전자치료, 세포배양육 등)

**FR-M6-002**: 논문/특허 데이터 수집 (P0, Must have)  
> 시스템은 Scopus, PubMed, USPTO API를 통해 기술별 논문 및 특허 데이터를 수집해야 한다.
> - 수집 주기: 월 1회

**FR-M6-003**: 임상시험 데이터 수집 (P1, Should have)  
> 시스템은 ClinicalTrials.gov API를 통해 임상시험 현황을 수집해야 한다.

**FR-M6-004**: 제품 출시 데이터 수집 (P1, Should have)  
> 시스템은 FDA 승인, 시장 출시 정보를 웹 크롤링으로 수집해야 한다.

#### 3.7.2 TRL 평가

**FR-M6-005**: TRL 자동 추정 (P0, Must have)  
> 시스템은 수집된 데이터를 기반으로 각 기술의 TRL을 자동 추정해야 한다:
> - TRL 1-3: 기초 연구 (논문 수 기준)
> - TRL 4-6: 실험실 검증 (특허, 전임상)
> - TRL 7-8: 실증 (임상시험)
> - TRL 9: 상용화 (제품 출시, 매출)

**FR-M6-006**: TRL 수동 조정 (P1, Should have)  
> 전문가는 자동 추정된 TRL을 검토하고 수정할 수 있어야 한다.

#### 3.7.3 대시보드

**FR-M6-007**: TRL 분포 시각화 (P0, Must have)  
> 대시보드는 다음을 표시해야 한다:
> - 기술 분야별 TRL 분포 (막대 그래프)
> - 국가별 TRL 비교 (히트맵)
> - TRL 변화 추이 (시계열)

**FR-M6-008**: 필터링 (P0, Must have)  
> 사용자는 기술 분야, 국가, 기간으로 필터링할 수 있어야 한다.

**FR-M6-009**: 드릴다운 (P1, Should have)  
> 사용자는 특정 기술을 클릭하여 상세 정보(논문 목록, 특허 목록, 임상시험 목록)를 확인할 수 있어야 한다.

#### 3.7.4 보고서

**FR-M6-010**: 분기별 TRL 보고서 (P1, Should have)  
> 시스템은 분기마다 주요 기술의 TRL 변화를 요약한 보고서를 자동 생성해야 한다.

### 3.8 Module 7: 예산 투입 변화에 따른 정책 수단 효과 분석

#### 3.8.1 시나리오 설정

**FR-M7-001**: 시나리오 입력 인터페이스 (P0, Must have)  
> 사용자는 다음 정보를 입력하여 예산 시나리오를 생성할 수 있어야 한다:
> - 시나리오 이름
> - R&D 예산 총액 (연도별)
> - 분야별 배분 비율 (레드/그린/화이트/그레이)
> - 민간 매칭 비율
> - 기타 정책 변수 (규제 강도, 인센티브 등)

**FR-M7-002**: 사전 정의된 시나리오 제공 (P1, Should have)  
> 시스템은 다음 사전 정의 시나리오를 제공해야 한다:
> - Base (현재 추세 유지)
> - 집중 투자 (특정 분야 강화)
> - 균형 배분
> - 민간 주도

#### 3.8.2 시뮬레이션 실행

**FR-M7-003**: SD 모델 연동 (P0, Must have)  
> Module 7은 Module 5의 SD 모델을 활용하여 시뮬레이션을 실행해야 한다.

**FR-M7-004**: 시나리오별 결과 산출 (P0, Must have)  
> 각 시나리오에 대해 다음 지표를 산출해야 한다:
> - 2034년 특허 수
> - 2034년 시장 규모
> - 2034년 고용
> - GDP 기여
> - 정부 투자 총액 (10년)
> - ROI (GDP/투자)

**FR-M7-005**: 복수 시나리오 동시 실행 (P1, Should have)  
> 사용자는 최대 5개 시나리오를 동시에 실행하고 비교할 수 있어야 한다.

#### 3.8.3 결과 비교 및 시각화

**FR-M7-006**: 시나리오 비교 표 (P0, Must have)  
> 시나리오별 주요 지표를 표로 정리하여 제시해야 한다.

**FR-M7-007**: 시계열 그래프 (P0, Must have)  
> 연도별 주요 지표 변화를 선 그래프로 표시해야 한다.
> - 각 시나리오는 다른 색상으로 표시

**FR-M7-008**: 레이더 차트 (P1, Should have)  
> 시나리오별 다차원 성과를 레이더 차트로 비교해야 한다.
> - 축: 효과성, 효율성, 형평성, 지속가능성 등

**FR-M7-009**: 히트맵 (P1, Should have)  
> 시나리오(행) × 지표(열) 매트릭스를 히트맵으로 시각화해야 한다.

#### 3.8.4 민감도 분석

**FR-M7-010**: Monte Carlo 시뮬레이션 (P1, Should have)  
> 각 시나리오에 대해 불확실성을 고려한 Monte Carlo 시뮬레이션(1,000회)을 실행하고, 95% 신뢰구간을 제시해야 한다.

**FR-M7-011**: 최악/기대/최선 시나리오 (P0, Must have)  
> 각 정책 시나리오에 대해 다음을 계산해야 한다:
> - 최악 시나리오 (경제 침체 + 기술 정체 + 규제 강화)
> - 기대 시나리오 (현재 추세)
> - 최선 시나리오 (경제 호황 + 기술 혁신 + 규제 완화)

#### 3.8.5 인터랙티브 시뮬레이터

**FR-M7-012**: 웹 기반 시뮬레이터 (P1, Should have)  
> 사용자는 웹 인터페이스에서 슬라이더를 이용하여 파라미터를 조정하고, 실시간으로 결과를 확인할 수 있어야 한다.

**FR-M7-013**: 결과 저장 및 공유 (P1, Should have)  
> 사용자는 시뮬레이션 결과를 저장하고, URL로 공유할 수 있어야 한다.

### 3.9 Module 8: 생명공학정책 생태계 건강도 진단

#### 3.9.1 건강도 지표체계

**FR-M8-001**: 지표 분류 (P0, Must have)  
> 건강도 지표는 다음 4개 범주로 분류되어야 한다:
> - 투입 (Input): R&D 투자 증가율, 인력 양성 규모
> - 과정 (Process): 기술개발 속도, 국제협력 활성도, 규제 적시성
> - 산출 (Output): 논문/특허 증가율, 기술이전 건수, 창업 기업 수
> - 성과 (Outcome): 시장점유율, 수출, 고용, 사회적 가치

**FR-M8-002**: 지표 데이터 수집 (P0, Must have)  
> 시스템은 각 지표에 대한 데이터를 다음 출처에서 수집해야 한다:
> - NTIS, 산업통계, 한국은행, 통계청
> - 수집 주기: 분기 1회

**FR-M8-003**: 지표 정규화 (P0, Must have)  
> 모든 지표는 0-100 척도로 정규화되어야 한다.
> - 방법: Min-Max Scaling, Z-score

#### 3.9.2 건강도 점수 계산

**FR-M8-004**: 가중치 설정 (P0, Must have)  
> 각 지표에 대한 가중치는 전문가 AHP 또는 관리자 직접 입력으로 설정되어야 한다.
> - 기본 가중치: 투입 25%, 과정 25%, 산출 25%, 성과 25%

**FR-M8-005**: 종합 점수 계산 (P0, Must have)  
> 건강도 종합 점수는 가중 평균으로 계산되어야 한다.
> - 공식: 종합 점수 = Σ(지표 점수 × 가중치)

**FR-M8-006**: 취약 영역 식별 (P0, Must have)  
> 점수가 50점 미만인 지표는 "취약 영역"으로 자동 식별되어야 한다.

#### 3.9.3 국제 비교

**FR-M8-007**: 국가별 건강도 비교 (P0, Must have)  
> 한국, 미국, EU, 중국, 일본의 건강도 점수를 비교하여 표시해야 한다.
> - 시각화: 레이더 차트, 막대 그래프

**FR-M8-008**: 순위 산출 (P1, Should have)  
> 종합 점수 기준 국가별 순위를 산출해야 한다.

#### 3.9.4 대시보드

**FR-M8-009**: 스코어카드 (P0, Must have)  
> 대시보드는 4개 범주별 점수를 카드 형태로 표시해야 한다.
> - 색상 코딩: 녹색(80+), 노란색(50-79), 빨간색(50 미만)

**FR-M8-010**: 레이더 차트 (P0, Must have)  
> 주요 지표의 점수를 레이더 차트로 시각화해야 한다.

**FR-M8-011**: 시계열 추적 (P0, Must have)  
> 건강도 점수의 분기별 변화를 선 그래프로 표시해야 한다.

#### 3.9.5 보고서

**FR-M8-012**: 분기별 진단 보고서 (P0, Must have)  
> 시스템은 분기마다 건강도 진단 보고서를 자동 생성해야 한다.
> - 내용: 종합 점수, 범주별 점수, 취약 영역, 개선 권고

**FR-M8-013**: 개선 권고 자동 생성 (P2, Could have)  
> 취약 영역에 대한 개선 방안을 GPT API로 자동 생성해야 한다.

### 3.10 Module 9: 정책 리스크 분석 및 의사결정지원시스템(DSS)

#### 3.10.1 정책 대안 입력

**FR-M9-001**: 대안 입력 폼 (P0, Must have)  
> 사용자는 다음 정보를 입력하여 정책 대안을 등록할 수 있어야 한다:
> - 대안명
> - 정책 유형 (예산, 규제, 인센티브 등)
> - 투입 예산 (금액, 기간)
> - 대상 분야
> - 예상 효과 (자유 기술)

**FR-M9-002**: 복수 대안 등록 (P0, Must have)  
> 사용자는 최대 5개 대안을 동시에 등록하고 비교할 수 있어야 한다.

#### 3.10.2 리스크 분석

**FR-M9-003**: Module 7 시뮬레이션 자동 실행 (P0, Must have)  
> 각 대안에 대해 Module 7의 시뮬레이션이 자동으로 실행되어야 한다.

**FR-M9-004**: 최악/기대/최선 시나리오 (P0, Must have)  
> 각 대안에 대해 최악, 기대, 최선 시나리오의 결과가 산출되어야 한다.

**FR-M9-005**: 표준편차 계산 (P0, Must have)  
> 각 대안의 결과 변동성(표준편차)을 계산하여 리스크 지표로 사용해야 한다.

**FR-M9-006**: 리스크 매트릭스 (P0, Must have)  
> 대안을 2×2 매트릭스(X축: 기대 효과, Y축: 리스크)에 배치하여 시각화해야 한다.

#### 3.10.3 다기준 의사결정 분석 (MCDA)

**FR-M9-007**: 평가 기준 설정 (P0, Must have)  
> 시스템은 다음 평가 기준을 지원해야 한다:
> - 효과성, 효율성, 형평성, 실현가능성, 지속가능성
> - 사용자는 기준별 가중치를 0-100% 범위에서 설정할 수 있어야 한다 (합계 100%)

**FR-M9-008**: 대안 평가 (P0, Must have)  
> 각 대안에 대해 평가 기준별 점수(0-100)를 입력하거나 자동 계산할 수 있어야 한다.

**FR-M9-009**: 종합 점수 계산 (P0, Must have)  
> 종합 점수는 가중치를 적용한 가중 평균으로 계산되어야 한다.

**FR-M9-010**: TOPSIS 분석 (P1, Should have)  
> TOPSIS 알고리즘을 이용하여 이상적 해와의 거리를 계산하고 순위를 도출해야 한다.

#### 3.10.4 민감도 분석

**FR-M9-011**: 가중치 민감도 분석 (P1, Should have)  
> 사용자는 가중치를 슬라이더로 조정하며 실시간으로 순위 변화를 확인할 수 있어야 한다.

**FR-M9-012**: What-if 분석 (P1, Should have)  
> 사용자는 특정 대안의 파라미터(예: 예산 규모)를 변경하고 점수 변화를 확인할 수 있어야 한다.

#### 3.10.5 의사결정 권고안 도출

**FR-M9-013**: 자동 권고안 생성 (P0, Must have)  
> 시스템은 다음 구조의 권고안을 자동 생성해야 한다:
> 1. 종합 평가 (1순위 대안 및 이유)
> 2. 리스크 고려사항
> 3. 권고 사항 (조건별 선택 가이드)
> 4. 후속 조치

**FR-M9-014**: 권고안 편집 (P1, Should have)  
> 정책연구자는 자동 생성된 권고안을 편집할 수 있어야 한다.

**FR-M9-015**: 권고안 승인 워크플로우 (P1, Should have)  
> 권고안은 센터장의 승인을 거쳐 최종 확정되어야 한다.

#### 3.10.6 보고서 생성

**FR-M9-016**: 비교 보고서 자동 생성 (P0, Must have)

## 4. 비기능 요구사항 (Non-Functional Requirements)

### 4.1 성능 (Performance)

**NFR-PERF-001**: 응답 시간 (Critical)  
> 사용자 요청에 대한 시스템 응답 시간은 다음을 만족해야 한다:
> - 페이지 로드: 95th percentile < 3초
> - 검색 쿼리: 95th percentile < 2초
> - 시뮬레이션 실행: 평균 10분 이내

**NFR-PERF-002**: 동시 사용자 (Critical)  
> 시스템은 최소 50명의 동시 사용자를 지원해야 한다.

**NFR-PERF-003**: 데이터 처리량 (High)  
> 시스템은 일일 1,000개 이상의 문서를 수집하고 처리할 수 있어야 한다.

**NFR-PERF-004**: 데이터베이스 쿼리 최적화 (High)  
> 복잡한 쿼리(조인 5개 이상)도 5초 이내에 완료되어야 한다.

**NFR-PERF-005**: 확장성 (High)  
> 시스템은 수평적 확장(Scale-out)이 가능해야 한다.
> - 컨테이너 기반 (Kubernetes)

### 4.2 가용성 (Availability)

**NFR-AVAIL-001**: 시스템 가동률 (Critical)  
> 시스템 가동률은 99% 이상이어야 한다.
> - 허용 다운타임: 월 7.2시간 이하

**NFR-AVAIL-002**: 백업 (Critical)  
> 데이터는 매일 자동 백업되어야 하며, 30일간 보관되어야 한다.

**NFR-AVAIL-003**: 재해 복구 (High)  
> 시스템은 재해 발생 시 4시간 이내(RTO)에 복구되어야 한다.

**NFR-AVAIL-004**: 데이터 복구 시점 (High)  
> 데이터 손실은 최대 1시간 이내(RPO)로 제한되어야 한다.

### 4.3 보안 (Security)

**NFR-SEC-001**: 인증 (Critical)  
> 모든 사용자는 로그인 후에만 시스템에 접근할 수 있어야 한다.

**NFR-SEC-002**: 권한 관리 (Critical)  
> 사용자는 자신의 역할에 따라 허용된 기능만 사용할 수 있어야 한다.

**NFR-SEC-003**: 데이터 암호화 (Critical)  
> - 전송 중: TLS 1.3  
> - 저장 시: AES-256

**NFR-SEC-004**: 비밀번호 정책 (High)  
> 비밀번호는 다음 정책을 만족해야 한다:
> - 최소 8자, 영문/숫자/특수문자 조합
> - 90일마다 변경

**NFR-SEC-005**: 세션 관리 (High)  
> 사용자 세션은 30분 비활동 시 자동 만료되어야 한다.

**NFR-SEC-006**: 감사 로그 (Critical)  
> 모든 사용자 활동(로그인, 데이터 조회, 수정, 삭제)은 로그로 기록되어야 한다.
> - 보관 기간: 1년

**NFR-SEC-007**: 침입 탐지 (High)  
> AWS WAF, GuardDuty 등을 활용하여 비정상적인 접근을 탐지하고 차단해야 한다.

### 4.4 사용성 (Usability)

**NFR-USAB-001**: 직관적 UI (High)  
> 신규 사용자는 30분 이내에 주요 기능(검색, 이슈 등록)을 사용할 수 있어야 한다.

**NFR-USAB-002**: 반응형 디자인 (High)  
> 시스템은 데스크톱, 태블릿, 모바일에서 정상 작동해야 한다.

**NFR-USAB-003**: 접근성 (Medium)  
> WCAG 2.1 Level AA 기준을 준수해야 한다.
> - 키보드 네비게이션 지원
> - 스크린 리더 호환

**NFR-USAB-004**: 다국어 지원 (Medium)  
> UI는 한국어, 영어를 지원해야 한다.
> - 언어 전환 기능

### 4.5 유지보수성 (Maintainability)

**NFR-MAINT-001**: 모듈화 (High)  
> 시스템은 9개 모듈이 독립적으로 개발·배포 가능하도록 설계되어야 한다.

**NFR-MAINT-002**: 코드 품질 (High)  
> 코드 커버리지는 80% 이상이어야 한다.

**NFR-MAINT-003**: 문서화 (High)  
> API는 Swagger/OpenAPI로 문서화되어야 한다.

**NFR-MAINT-004**: 로깅 (High)  
> 시스템은 구조화된 로그(JSON 형식)를 생성해야 한다.
> - 레벨: DEBUG, INFO, WARN, ERROR

**NFR-MAINT-005**: 모니터링 (Critical)  
> Prometheus + Grafana를 이용하여 실시간 모니터링이 가능해야 한다.

### 4.6 호환성 (Compatibility)

**NFR-COMPAT-001**: 브라우저 지원 (Critical)  
> 다음 브라우저 최신 2개 버전을 지원해야 한다:
> - Chrome, Firefox, Safari, Edge

**NFR-COMPAT-002**: 외부 시스템 연동 (High)  
> RESTful API를 통해 외부 시스템과 연동할 수 있어야 한다.

**NFR-COMPAT-003**: 데이터 포맷 (High)  
> JSON, CSV, Excel, PDF 형식의 데이터 입출력을 지원해야 한다.

### 4.7 규정 준수 (Compliance)

**NFR-COMP-001**: 개인정보보호법 준수 (Critical)  
> 개인정보 처리는 개인정보보호법을 준수해야 한다.

**NFR-COMP-002**: 전자정부법 준수 (High)  
> 시스템 구축은 전자정부법 및 정보시스템 구축·운영 지침을 준수해야 한다.

**NFR-COMP-003**: GDPR 준수 (Medium)  
> EU 데이터 처리 시 GDPR을 준수해야 한다.
